# PKG006 - RRECOMMENDS Package Validity

**Severity:** info

**Category:** packaging

**Enabled by Default:** Yes

---

## Description

Checks packages in RRECOMMENDS:pkg are defined in PACKAGES

The package list is read as for PKG004 and PKG005: `PACKAGES` and
`PACKAGE_BEFORE_PN` across continuation lines and local variables, `${PN}`
and the literal recipe name as the same package, the standard packages
(`-dev`, `-dbg`, `-doc`, `-staticdev`, `-locale`, `-src`, `-lic`, and
`-ptest` when a `ptest` class is inherited), packages classes create,
`PACKAGES_DYNAMIC`, and included files. The package is the first override:
`RRECOMMENDS:${PN}-dev[nodeprrecs]` and `RRECOMMENDS:${PN}-tools:append` are
for `${PN}-dev` and `${PN}-tools`.

Files under a `conf/` directory are not judged: a distro or machine
configuration sets RRECOMMENDS of packages other recipes create. Nor is a
file whose package list cannot be known (an include that cannot be found, a
`.inc` or `.bbappend` fragment, packages split off from Python).

## Example of Bad Code

```bitbake
# Recommend a package that is not defined
PACKAGES += "${PN} ${PN}-tools"
RRECOMMENDS:${PN} += "${PN}-extras"  # ${PN}-extras not in PACKAGES
```

## Why This Is Bad

Recommending non-existent packages results in ineffective or misleading dependencies. This can cause runtime expectations to be unmet and confuse integrators.

## How to Fix It

```bitbake
# Ensure recommendations reference existing packages
PACKAGES += "${PN} ${PN}-tools ${PN}-extras"
RRECOMMENDS:${PN} += "${PN}-extras"
```

Add the recommended package to `PACKAGES`, or remove the recommendation if the package is not meant to exist. Verify `RRECOMMENDS:<pkg>` only references valid packages.
